================================================================================
Intended use and limitations
================================================================================

--------------------------------------------------------------------------------
1. INTENDED USE
--------------------------------------------------------------------------------

AutoPYara is a defensive malware-analysis tool. It takes a collection of
samples believed to belong to the same family and automatically produces YARA
rules that match them, so that analysts can automate away the families that
yield to automation and spend their time on the ones that do not.

Intended users are malware analysts, threat-intelligence teams, and security
researchers who already possess samples and need detection signatures for them.

The tool READS sample files as byte streams. It does not execute, unpack,
emulate, deobfuscate, or otherwise run them. Handling a malicious file with
AutoPYara is therefore no more dangerous than reading that file with any other
program - but the samples themselves remain dangerous, and normal handling
precautions apply.

This artifact additionally lets readers regenerate the paper's figures from the
published evaluation data (claims 4-9) and reuse the figure scripts on new rule
sets laid out the same way (artifact/plots/README.md).

--------------------------------------------------------------------------------
2. DUAL-USE CONSIDERATION
--------------------------------------------------------------------------------

Automated signature generation is defensive by nature: its output is detection
rules. We are not aware of a meaningful offensive application of this tool.

The one adversarial consideration worth naming is that an attacker holding a
generated rule learns which byte sequences a defender keys on, and could mutate
those regions to evade it. This is a property of signature-based detection in
general, not of this tool specifically, and it is why generated rules should be
treated as one detection layer rather than a complete defense. The same holds
for the rules published in the evaluation data.

This artifact ships no malware (section 4, ethics.txt).

--------------------------------------------------------------------------------
3. LIMITATIONS
--------------------------------------------------------------------------------

The paper's rules cannot be regenerated from this artifact.
    They were generated from a malware corpus that cannot be redistributed.
    The artifact ships those rules with the TP rate each achieved; claims 4-9
    reproduce the paper's figures and numbers from them, deterministically.

The augmented pipeline is not bit-reproducible (claim 3).
    The augmented clustering path (preset="AutoPYara") derives cluster
    centroids using a randomized robust estimator whose partition step uses an
    unseeded random number generator. Two runs on identical input can produce
    different cluster counts and different rules; the seed cannot be fixed
    through the public API. Claim 3 therefore checks structural properties.
    Claims 4-9 are unaffected: they only read the provided rules.

Substantial memory requirement (claims 1-3).
    The JVM backend is started with a fixed 14 GB maximum heap, not
    configurable in the current release. See infrastructure/constraints.txt.
    Claims 4-9 do not start a JVM and need well under 8 GB.

Rule quality depends on input quality.
    The tool assumes the input samples genuinely belong to one family. Given a
    heterogeneous or mislabelled input set, it will still emit a rule, but that
    rule may be over-broad or of little practical value.

Rules generated from the synthetic proxy corpus are not useful signatures.
    They are structurally valid YARA and demonstrate that the pipeline works,
    but they match fabricated structure, not any real malware family.

Java dependency.
    A JRE 11+ must be present for claims 1-3. `pip install autopyara` succeeds
    without one, but constructing AutoPYara() then fails.

Platform coverage.
    Tested on Linux x86-64. The pinned environment needs Python 3.11 or 3.12
    (artifact/requirements-lock.txt); the Dockerfile provides one. macOS and
    Windows are untested, though nothing in the design is Linux-specific.

--------------------------------------------------------------------------------
4. ABOUT THE DATA IN THIS ARTIFACT
--------------------------------------------------------------------------------

Evaluation data (claims 4-9).
    Clusterings of the paper's malware corpus, every YARA rule generated for
    every cluster and configuration together with the TP rate it achieved, and
    the threat-hunting results. Published on Zenodo and fetched and verified by
    artifact/download_data.py. They identify samples only by name/hash and
    contain no malware. Details: provenance.txt; ethics: ethics.txt.

Synthetic proxy corpus (claims 1-3).
    Generated at run time by artifact/make_proxy_corpus.py. Each synthetic
    "family" is built around a large shared contiguous core wrapped in
    per-variant unique regions, mirroring the way real malware variants share
    reused code and embedded resources. It contains no malicious code, no
    real-world binaries, and no third-party data of any kind.

    The shared region is large and contiguous by design: an earlier version that
    planted small patterns at scattered offsets was invisible to fuzzy hashing,
    so the augmented pipeline saw no structure. Run the generator with --report
    to inspect the ssdeep similarity matrix.

    Because we constructed this corpus, it cannot support comparative claims:
    both pipelines reach a 6/6 TP rate on it. Comparative claims rest on the
    paper's evaluation, which claims 4-9 reproduce from the evaluation data.

To run AutoPYara against real samples instead, point `input_files` at a
directory of them; nothing in the tool is specific to the proxy corpus.
